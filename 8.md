**Explain how Kafka tracks message delivery?**

Apache Kafka tracks message delivery using a combination of partitioned logs, consumer offsets, and replication mechanisms. Unlike traditional message queues that track acknowledgments per message on the broker, Kafka uses a log-based model where delivery tracking is largely managed through offsets rather than individual message state.

At the core, Kafka stores messages in topics, and each topic is divided into partitions. Each partition is an ordered, append-only log. Every message written to a partition is assigned a unique, sequential offset. This offset acts as the message’s position within that partition. Kafka does not mark messages as “delivered” or “consumed.” Instead, delivery is determined by whether a consumer has processed messages up to a certain offset.

On the producer side, Kafka ensures durability and delivery guarantees through acknowledgments (acks). When a producer sends a message, it can request confirmation from the broker. If acks=0, the producer does not wait for confirmation. If acks=1, the leader broker confirms receipt. If acks=all (or -1), the leader waits until all in-sync replicas have replicated the message before acknowledging. This replication mechanism ensures the message is not lost even if a broker fails.

On the consumer side, Kafka tracks delivery through offset commits. Each consumer in a consumer group keeps track of the last offset it has successfully processed. These offsets are stored in an internal Kafka topic called __consumer_offsets. When a consumer processes messages and commits its offset, it is essentially telling Kafka, “I have successfully handled everything up to this offset.” If the consumer crashes, it can resume from the last committed offset.

Within a consumer group, Kafka assigns each partition to only one consumer at a time. This ensures that each message in a partition is processed by only one consumer within the group. If a consumer fails, Kafka triggers a rebalance, reassigning partitions to remaining consumers. The new consumer resumes processing from the last committed offset, maintaining delivery continuity.

Importantly, Kafka does not delete messages immediately after consumption. Messages remain in the log based on retention policies (time-based or size-based). This design allows consumers to replay messages by resetting their offsets. Because delivery state is offset-based rather than message-ack-based, Kafka supports different delivery semantics: at-most-once, at-least-once, and exactly-once (when using idempotent producers and transactions).

In summary, Kafka tracks message delivery indirectly through offsets maintained per partition and per consumer group. Producers ensure durability via acknowledgments and replication, while consumers control delivery state by committing offsets. This offset-based model makes Kafka highly scalable and fault-tolerant compared to traditional queue systems that track individual message acknowledgments.
