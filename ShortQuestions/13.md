**13. Explain how do we store sensitive user information such as password and credit card number in DB?**

1. Passwords

Passwords should never be stored in plaintext. Instead, we use hashing (and sometimes salting).

Step-by-step:

Hashing:

- A hash is a one-way function: it transforms data into a fixed-length string that cannot be reversed.

- Example algorithms: bcrypt, Argon2, PBKDF2, scrypt.

- Example: password123 → $2a$12$EIXwJoBzRq.g7yQn0nOq5O4yD0l7WbZ7mS3G2Jp8kIu7R

Salting:

- Add a random string (salt) to the password before hashing.

- Prevents attackers from using precomputed hash tables (rainbow tables).

- Each user should have a unique salt.

Storing:

- Store only the salt and hashed password in the DB, never the plaintext password.

Verification:

- When the user logs in, combine the entered password with the stored salt, hash it, and compare it to the stored hash.

2. Credit Card Numbers

Credit card numbers are highly sensitive and regulated under PCI DSS (Payment Card Industry Data Security Standard).

Best Practices:

- Do not store the full card number if possible.

- Prefer using a payment processor (Stripe, PayPal, etc.) that handles storage and tokenization.

Tokenization:

- Replace the real card number with a random token.

- Example: 4111111111111111 → tok_1HVxyzABC1234

- The token is meaningless if stolen, but your system can use it to charge the card via the payment processor.

Encryption (if you must store the card):

- Use strong symmetric encryption like AES-256.

- The encryption key must be stored securely, ideally outside the DB (HSM or Key Management System).

Store only what is necessary:

- Last 4 digits are usually stored for display: **** **** **** 1111

- Expiration date and card type can be stored if needed.

Access control:

- Limit who/what can access this data.

- Log and monitor all accesses.
