**19. Explain best practices to securely store secrets in applications.**


1. Never Hardcode Secrets

Problem: Storing secrets directly in code (e.g., String password = "1234";) risks exposure via source control, logs, or code leaks.

Best Practice: Keep secrets out of the codebase. Use environment variables, configuration files secured outside source control, or secret management tools.

2. Use a Secret Management System

Options:

Cloud-provided: AWS Secrets Manager, Azure Key Vault, Google Secret Manager

Open-source/self-hosted: HashiCorp Vault, Doppler, 1Password Secrets Automation

Benefits:

Secrets are encrypted at rest and in transit.

Automatic rotation and auditing.

Fine-grained access control.

3. Encrypt Secrets at Rest

Principle: All sensitive data stored (DB, files, config) should be encrypted.

Techniques:

Use strong encryption algorithms (AES-256).

Protect encryption keys separately from the encrypted data (e.g., KMS, Vault).

Example: Database credentials stored in a file could be encrypted with a master key fetched from a secure key store at runtime.

4. Protect Secrets in Transit

Principle: Secrets should never be sent in plain text over the network.

Best Practices:

Always use TLS/HTTPS for API calls.

Avoid passing secrets in URLs; use headers instead.

Use secure channels for inter-service communication (mTLS, VPN).

5. Use Environment Variables Carefully

Pros: Keeps secrets out of code; easy to change per environment.

Cons: Can be exposed in logs, process lists, or dumps.

Best Practice:

Limit who can access the environment.

Avoid printing env vars in logs.

Consider a small secrets wrapper library to load them safely.

6. Hash Passwords (Not Encrypt)

Important distinction:

Passwords → Hash (one-way function) + salt → never decrypt.

API keys/DB creds → Encrypt (two-way) if needed at runtime.

Recommended algorithms for passwords: Argon2, bcrypt, scrypt, PBKDF2.

Do not use: MD5 or SHA1 alone (too fast, vulnerable to attacks).

7. Rotate Secrets Regularly

Secrets should have a limited lifespan.

Rotation helps reduce risk if a secret is compromised.

Automate rotation wherever possible using your secret manager or CI/CD pipeline.

8. Implement Least Privilege

Each secret should only grant the minimal access necessary.

For example:

DB credentials for a read-only service should not have write access.

API tokens should only allow required endpoints.

9. Audit and Monitor Secret Usage

Log when secrets are accessed (without logging the secret itself).

Monitor for unusual usage patterns or access from unexpected hosts.

Use audit trails from secret management systems.

10. Avoid Committing Secrets

Tip: Use .gitignore for config files containing secrets.

Check for leaks: Tools like GitLeaks
 or TruffleHog
 can scan your repos.

If leaked: Rotate immediately.
