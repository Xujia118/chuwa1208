**Describe the different Docker network modes (bridge, host, none, overlay). When would you use each mode? What is the role of CNI plugins in Kubernetes networking?**


1. Bridge mode (default)

In Docker, bridge mode is the default networking mode for containers. When a container runs in bridge mode, Docker creates a private internal network (a bridge) on the host and attaches containers to it. Each container gets its own IP address within this bridge network, and Docker handles NAT (Network Address Translation) to allow external communication through the host. This mode is useful for most general container deployments where isolation is needed between containers and the host, such as running multiple web services on the same host without port conflicts.

2. Host mode

Host mode removes network isolation between the container and the host, meaning the container shares the host’s network stack directly. Containers in this mode use the host’s IP addresses and ports directly, without NAT. This mode is useful when low-latency network communication is required or when a containerized application needs to bind to a specific host port directly, such as monitoring agents or network-intensive services. However, it reduces isolation and can increase security risks.

3. None mode

In none mode, Docker disables networking for the container entirely. The container has no network interfaces except for a loopback interface. This mode is useful when you want full network isolation, such as running a highly secure service that does not need network access or when networking is managed manually by other means.

4. Overlay mode

Overlay mode is used for multi-host networking, typically in Docker Swarm or Kubernetes with certain CNI plugins. It allows containers running on different hosts to communicate over a virtual network as if they were on the same host. This is achieved by encapsulating container traffic (e.g., via VXLAN) and routing it across the physical network. Overlay mode is essential for distributed applications, microservices architectures, or clusters where containers must communicate across multiple nodes.

5. CNI plugins and examples

In Kubernetes, the Container Network Interface (CNI) provides a standard framework for configuring container networking. CNI plugins handle tasks like IP address allocation, routing, and network isolation. Different plugins implement different features and capabilities. Examples include Calico (for network policies and security), Flannel (for simple overlay networking), Weave Net (for encrypted multi-host networking), and Cilium (for advanced security and observability using eBPF). CNI plugins allow Kubernetes to remain flexible and modular, enabling cluster operators to choose the networking solution that best fits their requirements.
