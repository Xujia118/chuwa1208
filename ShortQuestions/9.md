**Explain the Circuit Breaker pattern. What are its three states, and how does it prevent cascading failures in a microservices architecture?**

It’s a resilience pattern used in microservices to protect a service from repeatedly calling another service that is slow or failing.

The three states of a Circuit Breaker

1. Closed (normal operation)

- Everything looks healthy.

- Requests flow normally

- Failures are counted

- If failures stay below a threshold → stay Closed

2. Open (fail fast)

- Too many failures detected → breaker opens.

- All requests are immediately rejected

- No calls are sent to the failing service

- Optional fallback logic runs (cached data, default response, etc.)


3. Half-Open (test mode)

- After a cooldown period, the breaker cautiously probes the service.

- Allows a small number of test requests

- If they succeed → transition to Closed

- If they fail → go back to Open


How it prevents cascading failures

1. Fails fast instead of blocking

When the breaker is Open, calls fail immediately:

- No waiting on timeouts

- No blocked threads

- No resource exhaustion

- This keeps the calling service healthy.

2. Isolates failures

A broken downstream service:

- Does not consume CPU, threads, or connections

- Does not drag down unrelated requests

- Failure stays contained.

3. Enables graceful degradation

Instead of total failure, you can:

- Return cached data

- Return partial results

- Show “temporarily unavailable”

- Users get something instead of everything breaking.
