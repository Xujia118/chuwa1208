**Prometheus uses a "pull" model for collecting metrics. Explain how this works and what are its advantages and disadvantages compared to a "push" model.**

Prometheus uses a pull-based model for metrics collection. In this model, each application or service (called a target) exposes an HTTP endpoint—typically /metrics—that returns its current metrics in a plain-text format. The Prometheus server is configured with a list of targets and periodically sends HTTP requests to each one at a defined scrape interval (e.g., every 15 seconds). When Prometheus scrapes a target, it retrieves the latest snapshot of metrics and stores them in its time-series database. Service discovery mechanisms (like Kubernetes, Consul, or static configs) help Prometheus dynamically find and update the list of targets.

One major advantage of the pull model is centralized control. Prometheus decides when and how often to scrape metrics, which simplifies configuration and ensures consistency across services. It also makes health monitoring easier: if a target cannot be scraped, Prometheus immediately detects it as “down.” Additionally, the pull model avoids pushing data blindly—Prometheus always knows the current state of each target. This model integrates well with dynamic environments like Kubernetes, where services frequently scale up and down.

Another advantage is simplicity and debuggability. Since metrics are exposed via HTTP, operators can manually inspect a target’s /metrics endpoint using a browser or curl. There is no need for complex client-side configuration to define where to send metrics. The model also reduces coupling, as applications only need to expose metrics and do not need to know about the monitoring system’s location.

However, the pull model has disadvantages. It can be problematic in highly ephemeral or short-lived jobs, because a job may terminate before Prometheus has a chance to scrape it. Prometheus addresses this with components like the Pushgateway, but that introduces additional complexity. Another limitation is that pull requires network accessibility: Prometheus must be able to reach each target, which can be challenging across firewalls, NAT boundaries, or disconnected environments. In large-scale systems, frequent scraping can also introduce overhead on both the Prometheus server and the targets.

In contrast, a push model (used by systems like StatsD or some cloud monitoring agents) has applications actively send metrics to a central server or collector. This works well for short-lived jobs and environments where targets cannot be directly reached. It can reduce scraping overhead and allow asynchronous buffering. However, push systems may struggle with detecting failed instances (since silence could mean either failure or no events) and can require more complex client configuration and coordination.
