**Explain the relationship between Trace, Span, and Context Propagation in distributed tracing.**

In distributed tracing, a trace represents the complete journey of a single request as it flows through multiple services in a distributed system. It is the top-level construct that captures the end-to-end lifecycle of that request—from the moment it enters the system (for example, via an API gateway) to all downstream calls (databases, microservices, external APIs) and finally to the response. A trace provides a holistic view of latency, failures, and dependencies across service boundaries, allowing engineers to understand system-wide behavior.

A span is the fundamental unit of work within a trace. Each trace is composed of multiple spans arranged in a parent–child hierarchy. A span represents a specific operation, such as handling an HTTP request, executing a database query, or calling another service. Spans contain metadata like start time, end time, duration, operation name, tags (key-value attributes), logs, and error information. The root span typically corresponds to the initial request, while child spans represent downstream operations triggered by that request. This hierarchical structure forms a tree (or sometimes a DAG) that models causal relationships between operations.

The relationship between trace and span is therefore compositional: a trace is a collection of related spans that share the same trace ID, and spans are the individual timed operations that make up that trace. Each span has its own span ID, and child spans reference their parent span ID. This structure allows tracing systems to reconstruct the execution flow and visualize it as a timeline or flame graph.

Context propagation is the mechanism that ties traces and spans together across service boundaries. In distributed systems, requests often travel over networks (e.g., via HTTP or messaging queues). To maintain a coherent trace, tracing metadata—such as the trace ID, span ID, and sampling decision—must be propagated alongside the request. This metadata is known as the tracing context. When a service receives a request, it extracts the context, creates a new child span using the same trace ID, and then injects the updated context into outgoing requests to downstream services. Without context propagation, each service would generate independent traces, breaking the continuity of the end-to-end view.

Together, these three concepts form the foundation of distributed tracing. The trace provides the end-to-end view, spans represent the granular operations within that view, and context propagation ensures that all spans across different services are correctly linked under the same trace. This coordinated structure enables observability platforms to reconstruct and analyze complex, multi-service workflows accurately.
