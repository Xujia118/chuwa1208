**What is the difference between range-based partitioning and hash-based partitioning? What problem does consistent hashing solve compared to simple hash-mod-N partitioning?**

1. Range-based partitioning

You split data by key ranges.

Example

- Node A: keys 1–1000
- Node B: keys 1001–2000
- Node C: keys 2001–3000

Pros

- Efficient range queries
(SELECT * WHERE key BETWEEN 1200 AND 1300 hits one node)

- Easy to reason about

- Preserves natural ordering

Cons

- Hotspots: If many requests target the same range, one node gets crushed
- Rebalancing is painful: Adding/removing nodes requires moving large contiguous chunks of data

2. Hash-based partitioning

You hash the key, then map it to a partition.

```
partition = hash(key) mod N

```

Pros

- Good load distribution
- No hotspots from skewed key patterns
- Simple logic

Cons

- Range queries are expensive
- A range spans all nodes
- Rebalancing is terrible with mod N
- Changing N reshuffles almost all keys

3. What problems does consistent hashing solve?

Simple hash-mod-N partitioning: the big problem

```
partition = hash(key) mod 4

Now you add a node:

partition = hash(key) mod 5

Almost every key moves to a different node!

```

This causes:

- Massive data movement

- Cache invalidation

- Thundering herds

- Downtime or degraded performance


Consistent hashing solves the rebalancing problem.

Key idea

- Both nodes and keys are placed on a hash ring

- A key goes to the next node clockwise

- When a node is added or removed, only nearby keys move

Result

- Adding/removing a node moves only

- ~1/N of keys, not all of them
