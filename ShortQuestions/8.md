**Why is "exactly-once delivery" considered impossible in distributed systems? How can you achieve "exactly- once processing" instead?**

“Exactly-once delivery” is considered impossible in distributed systems because you cannot distinguish between certain failure scenarios when messages travel over unreliable networks. In a distributed environment, components communicate over networks that can drop, delay, duplicate, or reorder messages. Suppose a sender transmits a message and does not receive an acknowledgment. It cannot know whether the message was lost in transit or whether the receiver processed it successfully but the acknowledgment was lost. If the sender retries, the receiver may process the same message twice. If the sender does not retry, the message might never be processed at all. Because of this fundamental ambiguity caused by network failures and partial crashes, you cannot guarantee both “no loss” and “no duplication” purely at the delivery level.

The core issue is that distributed systems operate under the possibility of partial failure. One node may crash while others continue running, and the network itself may partition. Even with protocols that use acknowledgments, retries, and timeouts, there is no perfect way to ensure that a message is delivered once and only once under all failure conditions. You can build systems that provide at-least-once delivery (messages may be duplicated but not lost) or at-most-once delivery (messages are not duplicated but may be lost), but combining both properties perfectly in an unreliable distributed environment is not achievable in practice.

Instead of aiming for exactly-once delivery, modern distributed systems focus on exactly-once processing. The idea is to accept that messages may be delivered multiple times, but ensure that processing them produces the same effect as if they were processed only once. This is usually achieved through idempotency and deduplication. Each message is given a unique identifier, and the receiving system keeps track of which IDs have already been processed. If a duplicate message arrives, it is detected and ignored or handled safely. As a result, even though the delivery may be at-least-once, the observable outcome is equivalent to exactly-once.

Another common technique involves transactional guarantees. For example, message consumption and state updates can be wrapped in a single atomic transaction. Systems like distributed logs combined with transactional databases allow you to commit the message offset and the state change together. If the transaction fails, both are rolled back; if it succeeds, both are committed. This ensures that a message’s effects are applied once, even if the message itself is delivered multiple times. In practice, exactly-once processing is about designing idempotent operations, maintaining deduplication records, and using atomic commits to make side effects safe under retries, rather than trying to make the network itself perfectly reliable.
