**When should you use multi-threading versus async/non-blocking I/O? Give specific examples of scenarios for each approach.**

When deciding between multithreading and async/non-blocking I/O, the key distinction is whether your bottleneck is CPU computation or waiting on external resources (I/O).

Multithreading is most appropriate for CPU-bound workloads—situations where the program spends most of its time actively computing. In these cases, the limiting factor is how much processing power you have available. For example, if you're performing image processing on thousands of photos, running physics simulations, encoding video, or doing heavy numerical computations (like risk modeling or machine learning inference), the CPU is doing continuous work. Adding more threads (up to the number of available cores) allows true parallel execution and better hardware utilization. In this scenario, async programming provides no benefit because there is no waiting to optimize—just computation to parallelize.

Async or non-blocking I/O, on the other hand, is ideal for I/O-bound workloads, where most of the time is spent waiting for something external—such as a database response, a network call, disk access, or another microservice. A classic example is a web server handling thousands of concurrent requests. Each request might involve querying a database and calling external APIs. The CPU does very little work per request, but each request spends tens or hundreds of milliseconds waiting. If you used one thread per request, you'd waste memory and incur heavy context-switching overhead. Async programming solves this by allowing a small number of threads (often just one event loop) to manage many concurrent connections efficiently while waiting for I/O readiness events.

A chat server or WebSocket service is another strong example of async being preferable. Thousands of clients may remain connected but idle most of the time, waiting for messages. Creating a dedicated thread per connection would be inefficient because those threads would mostly sit blocked. With non-blocking I/O, the system can handle massive concurrency without proportional thread growth.

It’s also important to understand that async does not make CPU-heavy work faster. If you run expensive computations inside an event loop, you can block the entire system and destroy responsiveness. In such cases, you would typically combine approaches: use async for handling network I/O and dispatch CPU-heavy tasks to a thread pool or worker processes.

In practice, modern backend systems are often hybrid. For example, a high-performance web server may use async I/O to handle connections efficiently while offloading CPU-intensive tasks—such as data processing or encryption—to worker threads. The guiding principle is simple: use multithreading to parallelize computation, and use async/non-blocking I/O to efficiently manage waiting.
