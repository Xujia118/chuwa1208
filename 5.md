**How to avoid duplicate consumption of messages?**

In systems like Apache Kafka, avoiding duplicate message consumption is mainly about how you manage offsets and processing guarantees.

First, understand why duplicates happen. Kafka guarantees at-least-once delivery by default, meaning a message will not be lost, but it may be processed more than once. Duplicates typically occur if a consumer processes a message but crashes before committing its offset. When it restarts, it resumes from the last committed offset and reprocesses the message.

One way to reduce duplicates is careful offset management. Instead of enabling auto-commit, consumers can manually commit offsets after successful processing. This ensures that offsets only move forward when processing is complete. However, even with manual commits, duplicates can still happen during failures — so offset control alone is not enough.

A stronger solution is idempotent processing. This means your business logic can safely handle repeated messages without causing incorrect results. For example, you can:

Use a unique message ID and store processed IDs in a database.

Use upserts instead of inserts.

Design operations to be naturally idempotent (e.g., “set balance to X” instead of “add $10”).

Kafka also supports exactly-once semantics (EOS) using idempotent producers and transactional APIs. When combined with transactional consumers (read-process-write pattern), this can guarantee that records are processed and written atomically, preventing duplicates in downstream topics. However, this is more complex and mainly applies when producing results back to Kafka.

In practice, the most reliable pattern is:

- Use manual offset commits.

- Make your processing logic idempotent.

- Use transactions if building Kafka-to-Kafka pipelines.

Ultimately, duplicate avoidance is less about stopping Kafka from delivering twice, and more about designing your system so that duplicate processing does not cause incorrect outcomes.
